The Challenge of Standard Model Training

• Generic COCO Limitation: Standard pre-trained models (YOLOv8n) only detect 80 basic items (cat, dog, apple, tennis racket) that are largely irrelevant for pedestrian mobility.

• Annotation Bottleneck: Manually labeling 50,000 bounding boxes across 92 custom classes would take 3+ months of human labeling and expensive local GPU server infrastructure.

• The YOLO-World Solution: We utilized yolov8s-worldv2.pt on Google Colab. YOLO-World combines a high-speed vision backbone with CLIP visual-linguistic pre-training. Calling model.set_classes(classes) injects our 92 text labels directly into detection heads via cosine similarity matching!

# 1. Setup Environment on Google Colab (Tesla T4 GPU)

# 2. Load Open-Vocabulary Base Model
from ultralytics import YOLOWorld
model = YOLOWorld('yolov8s-worldv2.pt')

# 3. Read 92 Assistive Vision Classes (Staircase, Door, etc.)
with open('classes.txt', 'r') as f:
    classes = [line.strip() for line in f if line.strip()]

# 4. Zero-Shot Semantic Embedding
print(f"Embedding {len(classes)} classes into vocabulary...")
model.set_classes(classes)

# 5. Export Standalone ONNX for Raspberry Pi 5
model.export(format='onnx', imgsz=320, dynamic=False, simplify=True)
Architecture Dilemma Engineered Resolution

Why Aren't We Using PyTorch Directly on the Raspberry Pi 5?

A detailed breakdown of why PyTorch is fatal for low-memory edge devices and why ONNX is mandatory.

❌ PyTorch (.pt) on Raspberry Pi 5 (Rejected)

• Massive RAM Overhead (~1.2 GB): import torch allocates 800MB–1.2GB instantly, consuming over 60% of total system RAM on a 2GB Pi 5.

• glibc Memory Arena Fragmentation: PyTorch creates up to 32 parallel memory arenas on 4 cores. Within minutes, memory fragmentation triggers Linux Kernel Out-Of-Memory (OOM) process termination.

• Unacceptable Latency (2.5 – 4 FPS): Dynamic graph evaluation on CPU incurs 300–400ms delay. A visually impaired person walking forward would collide before receiving warning audio.

• Bloatware: Requires downloading >2.5 GB of PyTorch binary wheels onto the microSD card.

✅ ONNX + OpenCV DNN on Pi 5 (Our Solution)

• Microscopic Memory (~35 MB): Static computation graph reduces memory footprint by 97%, leaving 1.8 GB free for the OS, camera stream, and audio.

• Zero Memory Fragmentation: Static input/output buffers are allocated once at boot and reused indefinitely with O(1) memory overhead.

• Smooth 18.5 FPS Real-Time Speed: OpenCV DNN compiles ONNX tensor operations into native 64-bit ARM NEON SIMD vector instructions on the Cortex-A76 cores.

• Zero External Dependencies: Built directly on OpenCV's native C++ DNN engine without needing PyTorch or CUDA.

Phase 2: Mathematical Optimizations ONNX Simplifier

Export Optimization Engineering: The 4 Key Flags

The mathematical transformations applied when converting from PyTorch to ONNX in Google Colab.

1. format='onnx' (Static Protobuf Standardization)

Replaces PyTorch's dynamic autograd execution engine with a standardized static computation graph stored in open Protobuf format. Strips out backward-pass gradients and training heads, leaving only lean forward inference kernels.

2. imgsz=320 (320x320 Input Resolution)

Downscales input frames to 320x320, requiring 4x fewer Multiply-Accumulate (MAC) calculations than 640x640. Tensors fit completely inside the Cortex-A76 L2 (512KB) and L3 (2MB) CPU caches, preventing slow RAM bus thrashing.

3. dynamic=False (Fixed Tensor Shape)

Locks the input tensor dimension permanently to (1, 3, 320, 320). This allows OpenCV DNN to pre-allocate memory buffers once during system boot, eliminating runtime dynamic memory allocations completely.

4. simplify=True (Layer Fusion & Pruning)

Executes ONNX-Simplifier to mathematically fuse adjacent Convolution + Batch Normalization + SiLU activation layers into single fused SIMD kernels, eliminating intermediate memory round-trips.
